# 第 1 轮评审结论

## 原始用户目标与可观察成功状态

依据工件自身可确认的目标：

- **部署者**配置分享能力后能够正常创建分享，不因缺失配置遭遇不可理解的 500。
- **管理员**在管理台与访客页看到同一失效时刻。
- **管理员**能在详情页重新查看并复制新建分享的完整链接；存量分享不可恢复时可重新生成。
- **管理员**可一次为多个邮箱分别创建互相隔离的链接。
- **管理员**可选择超过 7 天、但不超过安全上限的有效期。
- **访客**访问分享时受合理的限流、验证码和权限控制。

当前可观察成功状态尚未完全成立：批量原子性、凭据加密契约、KEK 注册、存量重新生成链路及长有效期语义仍存在阻塞性缺口。

## P0 问题

### A1【架构级】Goal → Outcome 链路不足以证明生产闭环

- **定位锚点**：`### 3.1 链路表(节点 | producer | consumer)`
- **问题**：表中缺少产出物、消费后状态和失败行为；部分“consumer”实际是存储列或验证命令。重新生成、解密审计、告警消费等关键路径也未进入链路。
- **问题根因**：链路以待改文件为中心，而不是以业务状态流转和最终可观察结果为中心。
- **业务影响**：可能出现新分享可解密但存量没有入口、日志已产生但无人告警、数据已写入但页面无法消费等“代码存在、业务不可达”情况。
- **架构影响**：无法验证 producer/consumer 配对，也无法识别死产出和错误消费者。
- **修改建议**：按固定模板补全每跳的 producer、artifact、consumer、result、failure；至少纳入新建分享恢复、存量重新生成、批量事务、Turnstile、告警触达和栅栏失败路径。
- **优先级**：P0

### A2【架构级】批量事务语义自相矛盾

- **定位锚点**：`不变量 I-3(批量)`
- **问题**：I-3 和测试要求“任一失败整批零残留”，接口出参却同时返回 `created[]` 与 `failed[]`，这是部分成功契约。
- **问题根因**：没有先决定批量操作究竟是原子事务还是逐项处理。
- **业务影响**：管理员无法判断失败后应重试整批还是只重试失败项；重试可能产生重复链接。
- **架构影响**：事务边界、幂等记录粒度、响应结构和前端状态机无法同时实现。
- **修改建议**：二选一并贯穿不变量、接口、事务、幂等、UI 和测试：全有或全无，或明确允许部分成功。若原子处理，定义验证前置、回滚及同键重放；若部分成功，删除“整批零残留”并定义逐项幂等。
- **优先级**：P0

### A3【架构级·安全】AES-GCM 决策缺少保证安全性的存储契约

- **定位锚点**：`技术边界(硬约束,执行者不得放宽)`
- **问题**：仅指定 AES-GCM、HKDF 和 kid 环，未定义密文 envelope、唯一 nonce、认证标签、AAD、版本号、kid 查找失败、密文损坏及轮换后的读取规则。
- **问题根因**：选择了算法，但没有建立持久化与解密协议。
- **业务影响**：nonce 重用可能破坏机密性；轮换或数据损坏可能使详情页错误地把安全故障当作普通“存量不可恢复”。
- **架构影响**：数据库 schema、加解密 adapter、轮换策略、错误码和迁移测试没有共同契约。
- **修改建议**：补充版本化 envelope 和关键不变量，区分“旧记录无密文”“KEK 暂缺”“未知 kid”“认证失败/密文损坏”，并明确哪些情况允许提示重新生成、哪些必须审计和告警。
- **优先级**：P0

### A4【生产接线】新建 KEK 能力未进入配置注册闭环

- **定位锚点**：`配置注册`
- **问题**：§1.4 要求新增 KEK 与 `kek_kid`，但配置注册和 T-11 只列既有五项，没有 KEK secret、kid、轮换或部署验证。
- **问题根因**：安全设计与部署工作包使用了不同的配置清单。
- **业务影响**：部署后新分享无法加密或查看链接，只能退化为重新生成。
- **架构影响**：新加密能力成为未接线产出，且 fail-closed 可能掩盖配置遗漏。
- **修改建议**：建立唯一配置清单，覆盖 KEK/KID 的本地、预览、生产注册方式、轮换顺序、缺失检测和部署验收；禁止把配置遗漏长期当作正常存量降级。
- **优先级**：P0

## P1 问题

### F1【可追踪性】多数成功状态缺少可审查的原始来源映射

- **定位锚点**：`来源:用户原话(问题一 / 问题二 / 四条需求)`
- **问题**：除凭据恢复外，多数目标只引用“问题一/问题二/四条需求”，当前工件中无法定位各目标对应的原话或用例后置条件。
- **问题根因**：来源以外部会话编号代替了工件内可验证摘要。
- **业务影响**：无法判断批量原子性、验证码和有效期续期究竟是用户目标还是执行者扩展。
- **架构影响**：技术手段容易反向成为验收标准。
- **修改建议**：为 A–H 分别补角色、操作、结果、负向条件和来源类型；不必复制完整需求，但必须能从本卡判断映射关系。
- **优先级**：P1

### F2【功能契约】Turnstile 启用与失败语义未定义

- **定位锚点**：`| POST /share/session`
- **问题**：token 被写成“可选”，但没有说明何时必填；验证码开关的来源、无 siteKey、token 缺失、校验失败、Turnstile 超时及服务不可用的行为均未确定。
- **问题根因**：只描述了组件接线，没有描述端到端策略状态。
- **业务影响**：可能出现前端显示验证码但后端不强制，或第三方故障导致所有合法访客无法访问。
- **架构影响**：前端开关、API 校验和基础设施 adapter 可能各自判断，形成多个真源。
- **修改建议**：明确单一启用判定、token 契约、稳定错误码、超时及降级策略，并补开启、关闭、无效 token 和上游故障场景。
- **优先级**：P1

### F3【产品边界】有效期核心语义仍未裁决，却被标为“不阻塞”

- **定位锚点**：`## 6. 遗留待确认(不阻塞评审,开工前需答)`
- **问题**：最大有效期、已建分享是否可续期、长有效期与 session TTL/maxSessions 的关系均未决定。
- **问题根因**：把决定用户最终可用性的产品约束当成实现参数。
- **业务影响**：即使 UI 允许 90 天，访问配额也可能提前耗尽；若真实需求是续期，只扩大创建档位并不能解决问题。
- **架构影响**：时间不变量、清理任务、配额模型、接口和测试基线都无法稳定。
- **修改建议**：将三项改为 T-22 前置阻塞决策，并用真实场景确定上限、续期语义以及长有效期下的会话/访问配额。
- **优先级**：P1

### F4【架构决策】缺少替代方案比较，存在 Solution-Jumping

- **定位锚点**：`### 1.3 三项用户已裁决的方向(2026-08-25 · 不可由执行者推翻)`
- **问题**：没有系统比较沿用现状、仅重新生成、可逆存储双轨，以及客户端循环调用既有 create 与新增批量端点等方案。
- **问题根因**：用户裁决被直接映射为具体接口和存储结构，没有区分业务结果与实现手段。
- **业务影响**：可能为“一次操作创建多条链接”引入不必要的服务端批量协议，或承担比用户目标所需更大的凭据恢复风险。
- **架构影响**：成本、可逆性、迁移风险和停止条件不可比较。
- **修改建议**：补沿用现状、局部调整、边界重构三档比较；尤其说明为何必须新增批量端点、为何双轨优于仅重新生成，并写明方案停止条件。
- **优先级**：P1

### F5【普通功能缺陷】E 项缺少真实业务影响和稳定错误契约

- **定位锚点**：`| E | 访问密钥启动报`
- **问题**：只说要提高“错误码可辨识性”，未说明哪个角色在什么操作中看到它、当前错误造成什么实际损失，以及目标错误码和 UI 行为。
- **问题根因**：把代码错误分类不清直接当成业务需求。
- **业务影响**：若没有用户可观察差异，该项可能只是技术洁癖；若确有运维误判风险，当前验收条件又不足。
- **架构影响**：API、日志、管理台可能各自发明不同错误表示。
- **修改建议**：补真实场景和缺失影响，归类为 B 稳定性保护并定义稳定错误码、HTTP 状态、日志和前端提示；答不出则删除本项。
- **优先级**：P1

## 断链、孤儿产出与错误消费者清单

1. `sec` 密文的 schema/envelope 未定义，创建服务的产出无法稳定被解密端点消费。
2. 重新生成被列为强制轨道，但没有链路表节点、接口契约、权限注册和 e2e。
3. `kek_kid` 设计存在，但部署配置及任务清单没有消费者。
4. 批量 API 的响应消费者按部分成功设计，而服务不变量要求原子失败。
5. `expires_at` 被写作 consumer；真正消费者应是管理台、访客页、清理任务和状态判断。
6. 告警事件有 producer，但 Cloudflare 告警规则、通知目标及触达验证没有形成最终 sink。
7. `git check-ignore` 是验证手段，不是 `.dev.vars` 安全结果的业务 consumer。
8. Turnstile token producer 与后端强制校验条件未建立同一真源。

## 生产业务场景推演

- **典型场景：新建单邮箱分享**  
  创建、时间显示和访客倒计时路径基本明确；链接再次查看受 KEK 注册和加密 envelope 缺口阻塞。

- **复杂场景：查看存量分享**  
  工件要求显示“不可恢复，可重新生成”，但重新生成未进入接口和注册闭环，当前不能证明管理员可完成操作。

- **复杂场景：批量中含一个越权邮箱并立即重试**  
  原子不变量与部分成功响应冲突，无法判断首次调用留下哪些记录、第二次应如何幂等。

- **极端场景：KEK 缺失、未知 kid 或密文被破坏**  
  当前都可能被折叠成“不可恢复”，会掩盖部署事故或数据完整性问题。

- **极端场景：Turnstile 开启但第三方超时**  
  没有明确 fail-open/fail-closed、错误码及恢复行为。

- **长有效期场景：90 天分享每 15 分钟重建会话**  
  文档自己指出可能提前耗尽访问配额，但没有裁决，因此“突破 7 天”不等于真实可用。

## 业务现实校验

| 新能力 | 分类判定 | 评审结论 |
|---|---|---|
| `sec` 可逆恢复 | A 业务刚需，同时增加安全风险 | 有明确管理员详情查看场景 |
| 存量重新生成 | A 业务刚需 + B 泄露处置 | 必需，但链路未闭合 |
| 批量创建 | A 业务刚需 | 业务结果成立；“必须新增单一批量端点”仍需方案比较 |
| 分享 Turnstile | B 稳定性保护 | 场景成立，策略契约不完整 |
| 创建端点限流 | B 稳定性保护 | 写路径保护合理 |
| 有效期上限 | B 稳定性保护 | 合理，但数值和配额关系必须先裁决 |
| 错误码可辨识性 | 暂无法分类 | 需补角色、操作和缺失影响，否则倾向 D |

| `.dev.vars` 忽略 | B 安全保护 | 合理，不是独立业务功能 |

## 架构判决

**调整边界。**

分享子系统的总体归属、双轨凭据恢复方向和栅栏前置思想可以成立，不需要推倒重设计；但必须先统一批量事务语义，建立完整的加密持久化协议和配置闭环，并补齐重新生成及告警的生产消费者。
