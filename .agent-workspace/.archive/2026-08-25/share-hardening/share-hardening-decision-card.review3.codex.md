# 第 3 轮评审结论

评审范围仅限 `share-hardening-decision-card.md`。未读取源码、Git 状态或目录外材料；涉及运行时、数据库和既有实现的事实均按工件自身陈述评估。

## 原始用户目标与可观察成功状态

工件呈现的目标基本明确：

1. 部署者按文档配置后能够正常创建分享，不泄露本地密钥。
2. 管理员与访客看到的失效时间指向同一物理时刻。
3. 管理员可以再次查看、复制当前有效的完整分享链接。
4. 管理员可批量为多个邮箱分别创建隔离链接。
5. 分享有效期可超过 7 天，但不能无限延长。
6. 分享验证码、限流和发布栅栏不能制造不可用或不可观测的生产断点。

可观察成功状态已覆盖管理台、访客页、部署流程和告警 sink，但以下关键链路仍存在自相矛盾或缺少生产消费者，因此目前不能证明全部目标能够闭环。

## P0 问题

### A1：批量重试契约无法同时满足

- **定位锚点**：`批量端点的两级失败契约(治「HTTP 恒 200 吞掉非法请求」)`
- **层次**：普通功能契约缺陷
- **问题**：工件同时规定：
  - 同一 `Idempotency-Key` 携带不同 `accountIds` 集合必须请求级拒绝；
  - UI 只能重试 `failed` 项；
  - 测试和 e2e 使用同一 key 只重试失败项。
  
  “只重试失败项”会改变 `accountIds` 集合，必然触发 payload 冲突。
- **问题根因**：整批请求指纹与逐项子幂等键之间没有明确谁是真正的幂等真源。
- **业务影响**：最重要的部分失败恢复路径会在生产中被拒绝，管理员只能换 key 重试并承担重复创建风险。
- **架构影响**：批量接口的幂等模型不可实现，UI、API 和测试指向不同协议。
- **修改建议**：在开工前二选一并贯穿接口、UI、测试和 e2e：重放原始全集，由服务端只执行失败项；或允许失败子集重试，并定义父 key/子 key 的合法继承及冲突规则。
- **优先级**：P0

### A2：KEK 缺失的失败语义仍有三套互斥结论

- **定位锚点**：`5. \`KEK 缺失时,查看链接端点返回「不可恢复」而非 500\``
- **层次**：架构级安全契约冲突
- **问题**：
  - §1.4 要求读取时返回“服务配置异常”，禁止伪装成“不可恢复”；
  - 测试 5 仍要求返回“不可恢复”；
  - 配置表又写成新分享无法加密后“详情页只能走重新生成”，与创建阶段必须拒绝矛盾。
- **问题根因**：R2 修正了主契约，但未同步测试和注册清单。
- **业务影响**：部署事故可能被错误当作正常存量降级，或静默创建不可回看的新分享。
- **架构影响**：fail-closed 不变量无法形成可执行门禁。
- **修改建议**：统一创建、批量创建、重新生成、读取、配置验收和测试五处语义；创建类写路径必须零写入拒绝，读取必须返回独立配置错误并告警。
- **优先级**：P0

### A3：加密协议不足以支持安全实现和密钥轮换

- **定位锚点**：`⛔ 密文持久化协议(选算法不等于定协议 · 执行者不得自行发明)`
- **层次**：架构级安全缺陷
- **问题**：
  - 只注册了单个 `SHARE_SEC_KEK`，却要求新旧 KEK 同时在环中；
  - 没有定义 KEK 是原始随机密钥、base64 编码密钥还是口令；
  - 提到 HKDF，但没有 salt、info、输出长度或是否实际使用的契约；
  - kid 同时存在于 envelope 和 `kek_kid` 列，未定义不一致时谁是真源。
- **问题根因**：算法选择、密钥材料格式、密钥发现协议和持久化协议被当成了同一层决策。
- **业务影响**：轮换可能导致历史链接突然不可恢复；不同实现者可能生成互不兼容的密文。
- **架构影响**：新的安全真源不唯一，半年后无法可靠解密或迁移。
- **修改建议**：在 ADR/决策卡中补齐密钥材料格式、KDF 参数或明确不使用 KDF、多 key 配置命名、当前 kid 选择规则，以及 envelope kid 与列 kid 的一致性不变量。
- **优先级**：P0

### A4：重新生成链路未接入可恢复存储

- **定位锚点**：`| L7 | 存量分享可重新生成 |`
- **层次**：架构级断链
- **问题**：L7 只描述产生新 `lid/sec` 和 `cv+1`，没有说明新 `sec` 会原子写入加密 envelope，也没有连接 reveal 端点。
- **问题根因**：轨二沿用了原“一次下发”的 regenerate 设计，但没有与本轮新增的轨一重新组合。
- **业务影响**：管理员重新生成后若关闭页面或首次响应丢失，仍可能无法再次查看“当前链接”，原始用户目标再次失败。
- **架构影响**：轨一和轨二成为两条平行实现，而非统一的凭据生命周期。
- **修改建议**：明确 regenerate 在成功时同步更新摘要、加密密文、kid 与版本，并说明 KEK 缺失时是否整体拒绝；其幂等重放应通过 reveal 链路恢复当前链接。
- **优先级**：P0

### A5：有效期上限尚未形成单一裁决

- **定位锚点**：`## 6. ⛔ T-22 前置阻塞决策`
- **层次**：普通功能与安全契约冲突
- **问题**：
  - I-2 已“裁定”内置 90 天；
  - §6 又把最大值列为待用户回答；
  - 配置表仍声称变量缺失会“无上限”；
  - TDD 项写当前用例“会通过”，但按工件描述当前无上限时，拒绝超长值的测试应当失败。
- **问题根因**：候选方案、当前事实和最终裁决没有分栏管理。
- **业务影响**：执行者可能实现无上限、固定 90 天或配置必填中的任意一种。
- **架构影响**：I-2 不是稳定不变量，部署验收无法判定正确结果。
- **修改建议**：把当前行为、推荐值和最终裁决明确分开；用户未裁决前保持 T-22 阻塞，裁决后一次性同步 I-2、配置表、测试和任务清单。
- **优先级**：P0

## P1 问题

### F1：Turnstile 的新增业务价值与工件自己的熵假设冲突

- **定位锚点**：`相对既有限流的增量`
- **层次**：架构级、Solution-Jumping
- **问题**：工件以分布式低频枚举 `sec` 证明验证码价值，但后文又明确 `sec` 为 2^256 空间。已知 `lid` 后枚举 256-bit `sec` 仍不构成现实攻击路径。
- **问题根因**：把“现有限流挡不住分布式低频请求”直接等同于“这些请求能够猜中凭据”。
- **业务影响**：访客承担额外交互、第三方依赖和 fail-open 分支，却未获得可量化的风险降低。
- **架构影响**：新增跨前后端能力可能属于 D 类技术洁癖。
- **修改建议**：补充真实的低熵目标、滥用成本或已发生攻击证据；若唯一目标仍是 256-bit `sec` 枚举，应删除本轮 Turnstile 接线或重新分类。
- **优先级**：P1

### F2：新增接口没有稳定错误码全集

- **定位锚点**：`### 3.2 新增/变更接口契约`
- **层次**：普通接口契约缺陷
- **问题**：reveal 的四类失败主要写成展示文案，Turnstile 只称“专用码”，批量 `failed[].code` 也没有枚举和稳定语义。
- **问题根因**：把 UI 提示、日志分类和 API 错误契约混在一起。
- **业务影响**：前端只能匹配文本或用不完整分支处理失败。
- **架构影响**：错误映射无法在 API 层形成稳定防腐层。
- **修改建议**：定义请求级和逐项级的稳定错误码、HTTP 语义及前端映射；展示文案保留在 i18n，不作为协议。
- **优先级**：P1

### F3：Owner 鉴权没有落实到对象级和租户级不变量

- **定位锚点**：`解密端点:仅 Owner 鉴权后可调`
- **层次**：架构级权限缺口
- **问题**：“Owner 鉴权”没有定义 Owner 如何由当前主体、租户和 `shareId` 共同判定；权限双表注册只能证明具备功能权限，不能证明能访问该分享。
- **问题根因**：功能级权限与资源级授权被合并描述。
- **业务影响**：错误实现可能允许同权限管理员跨租户查看或重新生成别人的链接。
- **架构影响**：敏感解密能力缺少不可绕过的对象级边界。
- **修改建议**：补充 reveal/regenerate 的对象归属查询、租户约束、越权错误语义及负例测试。具体数据关系需实现方核实。
- **优先级**：P1

### F4：历史时区数据画像不能可靠识别所有受影响行

- **定位锚点**：`L3 存量混合格式数据的裁决(修写入侧不会自动订正历史行)`
- **层次**：普通数据修复缺陷
- **问题**：以 `expires_at-create_time` 是否匹配合法档位识别时区错误，可能漏掉两个字段同时偏移的记录，也可能把自定义有效期误判为异常；统一减去“写入时区偏移”还隐含所有受影响记录来源时区相同。
- **问题根因**：业务时长差值被当作时间编码来源的确定证据。
- **业务影响**：可能遗漏仍显示错误的 ACTIVE 分享，或错误修改正常记录。
- **架构影响**：一次性修复会污染时间 SSOT，且文档已禁止兼容读，错误后缺少兜底。
- **修改建议**：要求实现方核实写入来源、部署时区和可区分字段，形成不会依赖合法档位猜测的画像规则；无法唯一识别时应停止 UPDATE 并报告。
- **优先级**：P1

### F5：加密测试未覆盖协议自身的核心不变量

- **定位锚点**：`T-20c 安全护栏补齐`
- **层次**：架构级测试缺口
- **问题**：现有三条安全测试没有覆盖密文篡改、跨 share 搬移、nonce 唯一性、新旧 kid 并存、未知版本及错误密钥。
- **问题根因**：测试仍集中在旧的“明文不可见”安全边界，没有验证新加密协议。
- **业务影响**：协议实现错误可能在正常 happy path 全绿时进入生产。
- **架构影响**：AES-GCM、AAD 和轮换规则只是文档声明，没有可执行门禁。
- **修改建议**：至少补认证失败、AAD 防搬移、轮换兼容和 nonce 唯一性测试；未知版本必须稳定拒绝。
- **优先级**：P1

### F6：配置与发布注册清单仍未真正收口

- **定位锚点**：`配置注册(唯一清单 · 本轮所有环境变量在此收口 · 新增能力不得另起清单)`
- **层次**：普通注册闭环缺陷
- **问题**：唯一表列出 7 个变量，但 L2、T-11 仍写 5 个；T-01 的告警前置又依赖尚未完成的 T-03 和仓库外告警消费者，却未明确执行顺序。
- **问题根因**：配置扩展和告警修复后，没有同步所有任务和门禁依赖。
- **业务影响**：README 或部署检查可能漏掉 KEK；栅栏核验可能在日志生产点尚未修复时被错误判定通过。
- **架构影响**：注册清单不是实际 SSOT。
- **修改建议**：用变量名清单替代数量描述，并明确 `T-03 → 告警规则落地验证 → T-01 判定通过 → T-30 开栅栏` 的依赖关系。
- **优先级**：P1

### F7：`.gitignore` 修复不足以证明已有密钥不会继续被提交

- **定位锚点**：`| L1 | 密钥不入库 |`
- **层次**：普通安全缺陷
- **问题**：`git check-ignore` 只能证明当前未忽略，不能证明 `.dev.vars` 从未被跟踪；已跟踪文件不会因新增 ignore 自动退出索引。
- **问题根因**：把忽略规则等同于完整的 Git 密钥防泄漏闭环。
- **业务影响**：部署者可能认为风险已修复，但历史或索引中的密钥仍可被提交。
- **架构影响**：无。
- **修改建议**：由实现方核实文件是否被跟踪、历史是否已有真实秘密；若被跟踪，补安全退出索引和凭据轮换处置。此事实本轮未查 Git，需实现方核实。
- **优先级**：P1

## 断链、孤儿产出与错误消费者清单

| 类型 | 位置 | 结论 |
|---|---|---|
| 断链 | L7 regenerate → L6 reveal | 新生成的 `sec` 未明确进入加密存储 |
| 断链 | 批量 UI → batchCreate | “只重试失败项”被整批 payload 指纹拒绝 |
| 错误消费者 | KEK 读取失败 → UI | 测试仍把部署事故消费为“不可恢复” |
| 错误消费者 | 历史时间画像 → UPDATE | 非唯一指纹可能选择错误记录 |
| 孤儿/不可执行规则 | KEK 多 key 环 | 唯一配置清单只注册一个 KEK |
| 潜在死产出 | 审计/告警事件 | Cloudflare 告警消费者仍待运维确认 |
| 注册遗漏风险 | L2/T-11 | 变量数量仍为 5，与唯一表的 7 项不一致 |

## 生产业务场景推演

1. **批量 10 项、3 项失败后点击“只重试失败项”**：请求集合改变，但 key 不变，按当前契约将请求级冲突，恢复路径不可用。
2. **存量分享重新生成后浏览器断网**：首次响应中的 `sec` 丢失；若 regenerate 未写加密列，管理员仍无法回看。
3. **部署遗漏 KEK**：正文要求创建失败，配置表却允许创建后降级，测试又期待“不可恢复”；生产行为无法预测。
4. **正常 KEK 轮换**：需要新旧两个 key 同时驻留，但配置只定义单个 secret，旧行可能提前失去可恢复性。
5. **生产库存在多个来源时区的历史行**：统一减 8 小时可能修改正常数据或漏掉同时偏移的记录。
6. **访客访问链接触发 Turnstile**：第三方故障时 fail-open 能保障可用性，但在 256-bit secret 前提下，正常工作时也未证明能显著降低现实风险。
7. **未配置有效期变量**：工件分别允许无上限、强制 90 天和等待用户裁决，无法形成验收结果。

## 架构判决

**调整边界。**

分享域边界、管理台/访客页 sink、部分成功模型以及凭据双轨方向可以成立，但凭据生命周期尚未统一：创建、批量、重新生成、加密存储、幂等重放和 reveal 必须收敛为一条权威链路。密钥环协议、有效期不变量和批量幂等契约也必须先定稿，不能交给执行阶段自行补齐。

Turnstile 需要重新通过业务现实闸门；在文档自己的 256-bit 熵假设下，当前理由不足以支撑新建该能力。
