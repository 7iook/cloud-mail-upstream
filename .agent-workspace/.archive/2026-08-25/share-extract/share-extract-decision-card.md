## 🏗️ 1. 边界决策

### 1.1 成功状态(用户原话转写 · 非自拟)

**NOT**「接了 AI 提取接口、加了链接正则」,
**BUT**「访客点开任意一封邮件,页面就地给出**这一封**里的验证码和/或验证链接;点到两者都没有的那封,明确说"未识别到验证码 / 验证链接",而不是把上一封的结果继续挂在那里」。

**负条件(必须不发生)**:页面上展示的码或链接,不属于当前选中的那封邮件。

**成立前提(评审 A2 补 · 缺了这两条就是空头承诺)**:

1. 全局提取模式**不为「关闭」**。默认值恰恰是关闭(§1.7),所以「开箱即得」不成立,验收与文档都必须先启用。
2. 该邮件是**启用之后新摄取的**。存量邮件不回溯(§1.6),它们恒为「未识别」——这是取舍不是缺陷,但不能藏在"任意一封"这四个字里。

**并列的交互需求**(同为用户原话,不属于提取管线,但同属本轮验收):手动刷新、新邮件 toast、复制全文。业务理由见任务清单 W-3。

**来源**:用户原话——「移除自动展示最新验证码逻辑:不自动拿最新邮件,用户点击哪一封,就解析哪一封邮件内容」+「二者任意一个有值就展示,都为空提示未识别到验证码 / 验证链接」。

### 1.2 提取的落点:摄取链,不是投影链

这是本卡最重要的一条,它决定了后面所有工作包的形状。

需求「AI 提取 + 降级兜底」看起来要在分享侧加一套提取器,但仓库里躺着这套东西**被砍掉的尸体**:`requirements.md` 的 AC-OTP-01/02/03/04/05/10/11/12/13 共九条,全部 `{status: deprecated, by: R2-A1}`,描述的正是一个 `DeterministicOtpScorer`——关键词邻近加权、排除样本降分、`@domain #code` 域绑定行、双路合并、HTML 转文本。

砍它的理由不是"打分器没用",而是位置错了。R2-A1 原标题:**「OTP 打分被放进分享投影链,形成第二套验证码真源」**。收缩时留下了明确出路(`requirements.md:162`):

> 若未来样本证明需增强识别,应把统一抽取/归一化移到**邮件摄取链**,使所有消费者读同一结果——**不在** Share 投影时重新推断

**本轮就是在执行这条出路,不是推翻它。** 因此:

- `Decision 6` / 不变量 `P-OTP-03`(分享投影只读 `email.code`,不得重新推断)**一个字不改**,新增的链接字段同样遵守;
- 提取能力全部加在摄取层,`email/email.js:95` 那一个调用点的位置不变;
- 附带收益:`telegram-service.js:64-69` 那个 code 消费者白拿到同样的改进,不需要知道分享的存在。

侦察报告判定此处「与既有决策正面冲突、必须先改 design.md」——**不采纳**。冲突的是"把提取塞回投影层"那种做法,不是提取能力本身。

### 1.3 四项用户裁决(2026-08-25)

| 议题 | 裁决 | 影响 |
|---|---|---|
| 提取模式能否 per-share 配置 | **否,做全局设置** | 摄取时系统还不知道这封邮件将来被哪个分享看到,per-share 提取模式在摄取侧无法表达。分享级只保留已有的 `otpExtractionEnabled`(是否展示结果) |
| 邮件原文是否要可配置隐藏 | **不做开关,默认展示整封** | 用户原话「邮件不需要藏着,本身也是需要暴露出去的,只会增加维护困难」。现状后端已全量下发 `text`/`content` 且渲染不删内容,故此项**零改动**,只补一个「复制全文」按钮 |
| AI 通道 | **仅 Workers AI,不引入外部 API** | fork 自部署者零额外配置。侦察建议的「档位 2:用户自填 OpenAI 兼容端点」**不做**——用户已明确排除 |
| 提取顺序 | **确定性优先 + AI 补位**(⚠️ 由用户原话「AI 优先」改判) | 见 §1.4 |

### 1.4 顺序改判:从「AI 优先」到「确定性优先」

用户初始需求原话是「AI 接口提取(优先) + 降级兜底方案」。侦察带回三条反向证据,用户据此改判。**记录改判依据,防止后续有人按原话回滚**:

1. **额度是账户级硬顶**:Workers AI 免费额度 10,000 neurons/天,Free 与 Paid 同额,超出后 Free 直接返回错误 3036(HTTP 429)。按最便宜模型、单封 2000 tokens 估,约 2,700 封/天;换 `llama-3.2-3b` 约 900 封/天。这是**整个账户**共享,不是每个 Worker 一份。
2. **确定性层无论如何都得写**:防注入要求 AI 的输出必须能在原文里逐字找到(§1.5),而这个回验本身就依赖确定性抽取出的候选集。既然它必须存在,让它先跑不增加任何工程量。
3. **确定性层零成本零注入面**:规则不吃额度,也不存在被邮件正文操纵的可能。

改判后 AI 的角色是**补位**:确定性层没把握时才花额度。两种顺序的最终准确率接近,差别在成本与攻击面。

### 1.5 链接的安全边界(评审 A1 重写 · 原稿此处有逻辑错误)

**原稿的错误**:把「输出确实来自原文」当成了「输出适合被提升为可信操作」。来源完整性 ≠ 链接安全性。攻击者就是发件人,他邮件里本来就摆着 `https://evil.example/x` 这个**真实锚点**,AI 从候选里选中它完全合规,页面照样把它渲染成「验证链接」按钮。原稿宣称已消除的 P0,其实没消除。

**先厘清风险的真实归属**:访客本来就能看到整封原文并点击里面的任何链接(用户已裁决不藏正文)。提取功能新增的**不是**"访客接触到恶意链接"这个可能,而是"页面把其中一条挑出来、放大、贴上标签"这个**背书动作**。风险来自背书,不来自 AI——纯规则提取同样会从攻击者的邮件里挑出一条。**因此这是功能级风险,不是 AI 级风险**,缓解也必须落在展示层。

四条不变量:

1. **协议白名单**:只接受 `http` / `https`。`javascript:` / `data:` / `file:` 等一律不予采纳(这条防的是脚本注入类,与钓鱼是两件事,都要防)。
2. **展示完整 URL,不只展示按钮**:访客必须看得见自己要去哪。把 URL 藏进按钮才是真正的背书。
3. **措辞只陈述来源,不做安全断言**:标签表达"这是从这封邮件里找出来的链接",不表达"这是安全的验证链接"。
4. **新窗口 + `noopener noreferrer`**:沿用 `safe-mail/srcdoc.js:89-90` 对正文锚点已有的同款处理,不给提取出的链接开后门。

**AI 任务形态的约束仍然保留**,但要如实表述它的作用范围——它把 AI 的输出空间限制在"原文已存在的东西"之内,**降低的是"AI 凭空生成一个原文没有的 URL"的风险**,不消除上面那条钓鱼风险:

- **链接**:AI 只能从 `document.querySelectorAll('a')` 得到的候选列表里**返回一个下标**。越界下标 = 判定失败,回落确定性结果。
- **验证码**:AI 返回的字符串必须能在原文纯文本里**逐字找到**,否则丢弃。

### 1.6 不回溯,且这是可接受的

提取在收信时执行,结果落库。**存量邮件不会被回溯补算**,它们的链接字段恒空,UI 表现为「未识别」。

不做一次性回填,也不做读时惰性补算。理由:分享的真实场景是「把邮箱给你,你去收**即将到达**的验证码」,存量邮件命中率低;而惰性补算会把 AI 调用搬到访客请求路径上,访客不受信任,等于把额度开销的触发权交给外人。列为可选后续,不在本轮。

### 1.7 提取模式:二态扩为三态,且默认态语义不变

现状 `setting.ai_code` 是二态且**默认关闭**(`entity/setting.js:53` 默认值 `1`,`entity-const.js:131-134` 的 `{OPEN:0, CLOSE:1}`)。按默认配置部署的人,`email.code` 恒为空串,分享页的码区块从不出现。

用户裁决「提取模式做全局设置」落到这里,正好把它扩成三态:

| 态 | 行为 | 成本 |
|---|---|---|
| 关闭 | 完全不提取(**现有 `CLOSE=1` 保持此语义**) | 零 |
| 仅规则 | 只跑确定性提取,不调 AI | 零 |
| 规则 + AI 补位 | 确定性优先,低置信时调 AI 补位(**现有 `OPEN=0` 升级为此语义**) | 少量 AI 额度 |

两条兼容红线:

1. **`CLOSE` 不得被悄悄改成"仅规则"**。它是默认值,改语义等于给所有存量部署静默开启一个新功能。
2. **`OPEN` 升级为"规则 + AI 补位"是待验证假设,不是既定结论**(评审 F2 修正)。原稿写"纯增强、不会更差"是错的:确定性层若产出一个**高置信的错误答案**,AI 就不会被调用,而原来 AI-only 时它可能是对的——存量 `OPEN` 部署有回归风险。故:
   - 必须定义**低置信阈值**,阈值以下才交给 AI;
   - 确定性结果与 AI 结果冲突时的取舍规则要写进实现;
   - 上线前用一批代表性真实邮件跑**新旧行为对比**,回归数为门禁,不是"看着差不多"。

### 1.8 ADR admission 与停止条件

**不需要新 ADR。** 理由:本轮沿 `Decision 6` 自己写明的演进路径执行,未确立新边界、未反转任何既有决策、不涉及难以回退的选型。承载物是 spec 内新增的 AC 与不变量。

(对照:上一轮凭据可逆化确实新立了 `ADR-share-credential-recoverability`,因为它推翻了原 ADR"sec 不可逆"的结论。两者性质不同。)

评审 F4 要求补替代方案权衡与停止条件。三条路各自的处置:

| 方案 | 处置 | 理由 |
|---|---|---|
| 沿用现状(只有 AI、无兜底) | 否 | 默认关闭 + AI 失败即空,用户报告的"不可靠"正源于此 |
| 投影层加提取 | 否 | 正是 R2-A1 判 P0 砍掉的形态,会造第二套真源 |
| **摄取链统一提取(本方案)** | 采纳 | Decision 6 自己指定的路径;所有消费者共享一份结果 |

**停止条件(命中任一即暂停并回报,不许硬推)**:

- 确定性层在真实样本上误提取率高到需要靠"再加一条规则"反复打补丁——说明启发式路线不适合,应退回"仅 AI + 展示未识别";
- 摄取延迟因提取显著上升(收信路径变慢),而超时保护(§3.1)仍压不住;
- §1.5 四条展示层不变量中任何一条无法落地——此时**砍掉链接提取、只保留验证码**,不带着未闭合的钓鱼面上线。

### 2.2 外部(见 `recon-ai-extract-feasibility.md`,含原始 query 与 URL)

采纳的业界做法,全部有出处,无自创:

- **`One-Time-Code:` 邮件头**:Apple 主笔的 IETF `draft-wells-origin-bound-one-time-codes-00` §3.2,格式 `One-Time-Code: code=123456; origin=example.com`。⚠️ **草案已过期、无 IETF 背书**,只作"命中即高置信"的快捷路径,必须假设 99% 邮件没有它。
- **意图闸门先于抽码**(Mailhook):先判主题/正文是否有验证意图再抽,避免任何一封邮件都吐出个"看起来像验证码"的数字。
- **关键词邻近打分**(`otp-detector`):三参数结构 `positiveKeywords` / `negativeKeywords` / `neighborhood`(候选前后约 80 字符)。
- **负向过滤清单**:电话、日期、门牌号、发票/订单/追踪号、年份。
- **长度依据**(NIST SP 800-63B):「as few as 6 decimal digits」,且 800-63-4 明确承认 Base64 等可打印 ASCII 形态——**所以不能只支持纯数字**。开源实现一致收敛在 4–8 位。

两条**否定结果**,记下来防止后人重复找:

- 用户提到的 `@BEGIN:VENDOR_VERIFIED` 标记:**搜索无对题结果**,未找到任何厂商公开规范使用它。不基于它做设计。
- **"如何判定哪条链接是验证链接"没有成熟规范或开源算法**。侦察报告给的加权打分方案标注为「本报告综合推导,非引用」。本卡采纳它但**明确其为自研启发式**,因此必须由测试用例锁定行为(§4),不能假定它天然正确。

## 📐 3. 接口契约

### 3.1 提取管线(摄取链 · 单次调用)

**输入归一化契约**(评审 F7 补 · 确定性层与 AI 层必须共享同一份语料,否则回验会假失败):

| 项 | 规则 |
|---|---|
| 正文真源 | `htmlToText(html)` 优先,为空时退 `formatText(text)` —— 沿用 `ai-service.js:14-16` 既有优先级,不新造 |
| 锚点候选 | 只从 `html` 的 DOM 取;纯文本邮件无锚点候选,链接提取直接判未识别 |
| 截断 | 纯文本截至上限(现值 6000,`ai-service.js:16`);**截断只作用于送 AI 的语料,确定性层扫描完整文本**,避免码/链接落在尾部被切掉 |
| 共享 | 归一化只做一次,两层复用同一份文本与同一份锚点集合 |

```
0. 能力探测:env.ai 为 undefined(fork 未加 [ai] 绑定)时标记 AI 不可用,不抛
1. 解析一次:linkedom parseHTML → { 归一化文本, 锚点候选集 [{href, text}] }
2. 快捷路径:One-Time-Code 邮件头命中 → 采纳其 code
   ⚠️ 字段级完成,不终止管线(评审 F1):它只提供 code,link 必须继续走后续
3. 确定性层(按字段各自求解):
   ├ code(若未由步骤 2 敲定):意图闸门 → 邻近打分 → 负向过滤 → 长度 4-8(含字母数字混合)
   └ link:锚点候选按 href path 关键词 / 锚文本 / token 长度打分,负向过滤退订·隐私·社交
       并施加 §1.5 协议白名单(非 http/https 直接出局)
4. AI 补位:逐字段判断,仅对「该字段仍为空或低于置信阈值」的那个字段发起
   ├ 前置:模式=规则+AI 且 AI 可用
   ├ 任务形态 = 选择题(link 返回候选下标;code 必须能在归一化文本里逐字找到)
   └ 失败处理见下
5. 落库:email.code(已有) + email.verify_link(新列)
```

**AI 调用的资源与失败契约**(评审 F3 补 · 这是收信路径,卡住会阻塞邮件入库):

- **超时**:必须设上限并在超时后放弃 AI 结果,继续用确定性结果落库。收信不能等 AI。
- **输入上限**:送 AI 的语料受上表截断约束,不把整封大邮件塞进去。
- **失败分类**(不可合并成一个 catch):`env.ai` 缺失(未绑定) / 429 额度耗尽 / 超时 / 返回非法 JSON / 越界下标 / 回验不通过。
- **可观测**:用户路径静默降级,但运维侧不能静默——失败要能被区分和计数,否则管理员无法分辨"规则没识别出来"和"AI 已经挂了一周"。指标不得含邮件正文。

### 3.2 链路表(评审 A2 重写 · 补 artifact / 结果 / 失败行为 / 字段映射)

| 跳 | Producer | Artifact | Consumer | 消费后结果 | 失败行为 |
|---|---|---|---|---|---|

**最终落点**:第 7、8 跳。**真实 e2e 姿势**:

1. 先在系统设置把提取模式设为「仅规则」(或「规则+AI」)——**这一步不能省**;
2. 本地起 worker + 前端,向绑定邮箱投四封:仅含码 / 仅含验证链接 / 两者皆有 / 两者皆无;
3. 逐封点击,核对展示值属于当前那封、"未识别"文案正确出现;
4. 额外投一封含 `javascript:` 锚点的,确认它不被采纳。

### 3.3 新列与发布顺序

`verify_link text default '' notNull`,与 `code` 同形(空串 = 无,非 null)。迁移走 `v3_4DB`,沿用 `init.js` 既有 expand-only 幂等模式。

**发布顺序(评审 F6 补)**:本项目迁移由人工访问 `GET /api/init/{jwt_secret}` 触发,**不随部署自动执行**,所以顺序是真实风险而非形式主义:

1. 先部署带 `v3_4DB` 的 worker 并**访问 init 端点跑迁移**;
2. 迁移未跑而新代码已上 → 写入新列会失败。摄取侧对此需容错:**新列写入失败不得阻断邮件入库**(邮件本身比提取结果重要);
3. 前端消费 `link` 字段前先判空,老后端不下发该键时按未识别处理——前后端可乱序上线;
4. **回滚**:worker 回退到旧版本后,新列留在表里不删(expand-only 的意义),旧代码不认识它,行为退回原状。无需数据清理。

- 非 `http`/`https` 协议的链接不得渲染成可点击入口。

**提取管线**

- AI 抛异常 / `env.ai` 为 undefined / 429 / 超时 / 返回非法 JSON / 返回越界下标 / 返回原文中不存在的码 → 七条路径均落到确定性结果,**不得**抛给调用方,**不得**返回 AI 的脏值。
- **超时用例**:AI 迟迟不返回时,落库仍在限定时间内完成(证明收信不被阻塞)。
- **组合用例(F1)**:同封邮件含 One-Time-Code 头 + 正文验证链接 → 两个字段都要有值。
- 模式=关闭 → 完全不提取(证明默认部署行为未变)。
- 模式=仅规则 → 不产生任何 `env.ai` 调用(用 spy 断言零调用,而非断言结果)。
- 确定性层:纯数字 4/6/8 位、字母数字混合、带连字符;电话/日期/年份/订单号**不得**被当成码。
- 链接:退订、隐私政策、社交图标链接**不得**被当成验证链接;`javascript:`/`data:` 锚点必须出局。这是自研启发式,用例即契约。
- **归一化(F7)**:纯文本邮件(无 html)、HTML-only 邮件、码位于截断边界之后 —— 三种形态各有用例。

**投影**

- `otpExtractionEnabled=false` 时 `code` 与 `link` 两个键都**不出现**(不是 null 占位)——沿用 `share-mail-service.js:103-105` 已有的注释约定。

**升级兼容(F2)**

- 一批代表性真实邮件上跑新旧行为对比,确定性假阳性导致的回归数为门禁。
