## 总体结论

工件对后端顺序重放、配额不重复消耗、KV 失败降级、TTL 与日志泄漏给出了较好的单元/HTTP 测试证据；幂等恢复也有明确的真实场景，属于 **B 稳定性保护**，不是为了接口对称而新增的技术洁癖。

但它尚不能证明“Session 建立幂等恢复”真实完成：报告没有先界定原始目标究竟是“T-07 后端子任务完成”还是“用户响应丢失后可恢复”，已明确前端入口未接线、返回 token 未走到最终消费者，而且“`max_sessions=1` 同 key 重试必须成功”与“跨 PoP 缓存未传播时会再次走配额”没有闭环。完成判决应为：**局部完成但链路未闭环**。

## 主要发现

### A1 [P0] 原始目标、验收边界与完成判决缺失

- 锚点：`## 1. 红 → 绿`
- 层次：完成性闸门
- 问题：文档从测试红绿直接展开，没有把原始失败前状态、用户可观察成功判据、T-07 子任务边界逐项映射到证据，也没有模板要求的“真实完成 / 局部完成但链路未闭环 / 未解决原始目标”判决。`T-07 入库` 只能证明代码交付，不能证明目标完成。
- 问题根因：报告按实现文件和测试数量组织，而不是按 Goal → Outcome 组织；同时把前端接线划给 T-26，却没有说明这对本报告完成口径的影响。
- 业务影响：读者无法判断当前交付是否已让访客在响应丢失后恢复，还是仅提供了一个尚未被真实入口使用的后端能力。
- 架构影响：producer、transport、缓存、quota、token consumer 的责任边界没有形成可审计闭环。
- 修改建议：在红绿证据前补齐目标—证据矩阵，明确原始场景、失败状态、每项成功判据、任务内/任务外边界；在报告结尾给出完成判决。若目标仅限后端 T-07，应明确声明“局部完成”，不得用该证据外推完整用户链路。

### A2 [P0] 已知跨 PoP 行为与 AC-SESS-10 恢复承诺互相冲突

- 锚点：`## 3. 与既有裁决的对齐`
- 层次：架构级
- 问题：工件一方面写明 `max_sessions=1` 响应丢失后同 key 重试必须成功且 `used_sessions` 恒 1；另一方面承认跨 PoP 最长 60 秒可能读不到缓存并退化为再次走配额。按工件给出的调用顺序，首发已占满最后一个 slot 后，跨 PoP miss 可能在配额判定处拒绝重试。这不是单纯“多消耗一格”，而可能直接否定恢复结果。并发同 key 的双 miss 也没有结果。
- 问题根因：将最终一致 KV 当作幂等结果真源，但验证只覆盖同一 mock KV 上首发完成后的顺序命中，没有验证存储可见性窗口和 check-then-act 竞争。
- 业务影响：最需要幂等保护的响应丢失/重试场景仍可能失败，用户会在额度已被首发消耗后拿不到首发结果。
- 架构影响：幂等语义的保证范围不明确；当前证据无法区分“全局幂等”“单 PoP 尽力重放”或“最终一致下允许失败”。
- 修改建议：需实现方核实是否存在请求亲和、强一致存储或其它机制消除该路径。报告应给出跨 PoP/并发同 key 的可复现实验结果，并将结果与 AC-SESS-10 明确对照；若该退化已被规格正式接受，应引用裁决并把保证边界写进完成判决，否则不得判定目标完成。

### B1 [P1] 所谓 HTTP E2E 停在 producer，未证明正确消费者与真实入口

- 锚点：`### R-T07-5 · [P3 · 非漏登记] 前端侧未接线`
- 层次：功能链路
- 问题：HTTP 用例证明接口返回同一 token 与 `access_count` 不变，但没有让 token 继续进入 `resolveSession`/实际访问接口；真实访客页也尚不发送幂等键。把前端工作登记在 T-26 可以解释任务分工，不能替代本模板要求的 last-mile 证据。
- 问题根因：测试边界以 API 响应为终点，把“产出 token”当成“恢复会话”。
- 业务影响：即使 token 重放值相同，也不能排除 token 无法消费、响应字段陈旧影响客户端、或真实入口根本不触发重放能力。
- 架构影响：生产者—消费者契约和前端—API 接线未被验证。
- 修改建议：补一条从真实入口到 token 消费结果的链路证据；若该链路必须等 T-26，当前报告应显式列为未验证并维持“局部完成但链路未闭环”，不要将“非漏登记”等同于“已完成”。

### B2 [P1] 测试计数互相矛盾，证据无法唯一复现

- 锚点：`## Update Log`
- 层次：证据完整性
- 问题：绿段给出两个目标文件合计 40 条；随后又说原地复跑 service 为 33/33、API 为 7/7，仍为 40；Update Log 却称独立复跑 34/34 + 7/7，共 41 条。报告未解释多出的一条、运行时 revision 或过滤范围。
- 问题根因：多次运行结果被汇总时没有为每次读数绑定 commit、命令和测试集合。
- 业务影响：审阅者无法确认哪一组数字对应提交 `c2087ce`，也无法把日志与完成声明一一对应。
- 架构影响：无直接架构影响，但削弱整个验证报告的证据可信度。
- 修改建议：统一计数，或逐次列明 commit、覆盖文件、完整命令、测试文件数与用例数，并解释 40/41 的差异。

### C1 [P2] 超长幂等键风险已有事实依据，但处置与验收状态悬空

- 锚点：`### R-T07-3 · [P2] Idempotency-Key 未做长度/字符集约束`
- 层次：稳定性/运维
- 问题：报告已指出客户端可造成 KV `put` 持续失败并刷 `share.system.error`，但只写“建议与 T-08 一并定”，没有负责人、明确决策或验证门槛。
- 问题根因：把已识别的输入边界风险作为开放建议记录，没有纳入完成判决的副作用清单。
- 业务影响：可能形成可重复触发的日志噪声与额外 KV/观测成本；是否可被请求层大小限制或限流覆盖，需实现方核实。
- 架构影响：外部输入直接进入存储键，边界责任未明确。
- 修改建议：记录明确 owner/裁决，并验证现有请求大小限制或增加对应边界证据；若由 T-08 处理，应列为本次接受的剩余风险而不是悬空问题。

- 干净隔离 worktree 上报告全量 17 个测试文件、221 条通过，且说明既有断言无删除/改写；这是有效的提交级回归证据。

- `/workspace` 当前组合状态的全量测试为红，工件将其归因于并发 T-12 改动；隔离结果能证明 T-07 相对基线，但不能证明与 T-12 合并后的集成状态。
- 未提供真实 Workers KV 的延迟、跨 PoP 可见性、并发竞争、日志量或成本证据。

## 未验证或证据不足项

1. 原始用户目标及 T-07 与完整 Session 恢复能力之间的完成边界。
2. 浏览器真实入口生成、持久化和重用 `Idempotency-Key`。
3. 重放 token 被最终消费者成功使用并恢复用户访问。
4. 跨 PoP 缓存不可见与并发同 key 双 miss 下的业务结果。
5. 吊销、过期、权限变化后的实际消费结果，而非仅代码路径推断。
6. 超长 key 的输入边界及日志/成本副作用。
7. 40 与 41 条测试读数的可复现解释。
