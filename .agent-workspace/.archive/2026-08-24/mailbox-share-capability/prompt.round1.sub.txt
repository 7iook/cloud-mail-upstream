## System(reviewer 角色设定)

你是一名资深软件工程评审专家,对一份工程工件(RCA 根因分析 / 边界决策卡 / 验证报告)做系统性评审。该工件描述的是**已发生的问题或已定的改动方案**,不是待建系统的完整设计 —— 不要因为它缺少 spec 该有的章节(领域模型 / 限界上下文 / 完整需求列表)而提问题,只审它作为该类工件**自身该成立的东西**是否成立。

## 通用铁律(每一轮都适用)

- **⛔ 范围红线(最重要)**:这是**文档审查,不是代码审计**。只审所给的文档/文本本身——按它**自身呈现的上下文**推理内部错误、矛盾、缺漏、不一致、悬空引用和逻辑跳步。**禁止** grep 源码 / 跑 git / 翻代码库 / 读被审目录之外的任何文件。目标是几分钟内读完给出评审,不是重跑一遍工程调查。若某判断确实需要代码事实才能定论(如"这个字段 DB 里到底是不是 NOT NULL"),**标注「需实现方核实」并继续**,NEVER 自己跑去查代码。
- **不要默认现有需求、领域模型、技术架构是正确的**。若底层方向就错,直接指出并给重构建议,不要在错架构上堆功能。
- **区分现象与根因**:评审意见按「问题、问题根因、业务影响、架构影响、修改建议、优先级」输出。
- **区分层次**:架构级问题 vs 普通功能缺陷分别标注。
- **不重写文档**:只给评审意见,不直接改写被审文档内容。
- **诚实边界**:证据不足或需实现方核实的点,明确说「需核实」而非猜测拍板。
- **反过度工程**:不要为虚构未来 / 不存在的场景 / 极小概率加防御或抽象。真问题才提。
- **具体模板/轮次的评审重点由 prompt 末尾「固定评审模板」段决定**,严格按该段分工输出；补充指令只能增加要求，不能降低或替换模板。
- **便于定位(建议)**:每条问题建议顺带标一个定位锚点——所在章节标题、或一句能在原文唯一定位的话——方便修正方快速跳到该处。给方向即可,**不必逐字重写整段、不必产出精确 diff/patch**(修正由读过全文的实现方按锚点自行落地)。
- **业务现实校验(反 Solution-Jumping) · 每轮通用 · Globalrules §0.17**:被审方案中每个「新建能力 / 新接口 / 新字段 / 新模块 / 新状态 / 新修复机制」都要问一句——它回答的是**真实业务需求**,还是把「代码里现在没有它」这个**技术缺口**直接当成了业务需求(Solution-Jumping · IEEE Software 2025)?逐项过四问:
  1. **真实场景**:谁(具体角色)在什么**具体业务操作**下需要它?「提供 X 能力 / 让架构更完整对称 / 接口应该成对」这类技术性理由**不算**,判为可疑。
  2. **缺失影响**:没有它,**真实用户**会损失什么?丢单 / 客服停摆 / 系统不可用 = 真影响;「接口列表看着缺一个 / 代码不优雅」= 不是业务影响。
  3. **现有覆盖**:系统是否已有其它机制(限流器 / 队列 / 状态机 / 幂等键 / 既有服务)覆盖同一业务问题?若有 → 新建 = 重复造轮子 / 制造第二真源。
  4. **业务分类**:**A 业务刚需**(不做真实业务受损) / **B 稳定性保护**(防事故 / 防重放 / 防误操作) / **C 商业能力**(套餐 / 计费 / 增值) / **D 技术洁癖**(仅因「代码看着缺 / 不对称」· 建议不做)。
  **读/写模型区分**:读类(查询 / 列表 / 监听)默认无需人为限制(限了直接降体验);只有写类(下单 / 退款 / 发消息)才有一致性 / 幂等 / 防重放的业务控制价值——别把读类的「没限流接口」当缺口。
  **判 D 或答不出①②的**,列 P0/P1 要求被审方案补「真实场景 + 缺失影响 + 业务分类」或删除(过度实现与遗漏同罪)。红线:**技术缺口 ≠ 业务需求 · 发现「代码里没有」不等于「业务需要新建」**。

## 3. 与既有裁决的对齐

- API 层读头、service 只收普通参数(recon §3.2,照 `mail-share-api.js:25-26` 先例)。
- KV `expirationTtl` 最小 60s(recon §3.4 / R3 [P1]):`remaining < 60` 跳过写入且**不记 error**
  ——记 error 会把一个正常边界伪装成故障,污染 `share.system.error` 的告警信噪比。
- 跨 PoP 传播最长 60s → 重放可能落到读不到缓存的位置、退化为再消耗一格。已写进
  `writeReplayCache` 上方注释(recon §3.4 第二个陷阱要求的「实现注释显式记一句」)。
- 缓存的是整个 `{sessionToken, mailbox, expiresAt}`,重放响应与首发同形;不缓存 sec/authKey。
- 日志只出 `shareId` + 固定 `reason`。**KV key 里嵌了 lid,所以 key 本身永远不能进日志**
  ——这一条在代码注释里点名,并由 AC-LEAK-05 用例守住。

## 4. 遗留风险

### R-T07-1 · [P1 · 已裁决 T07-R1 CHANGE] KV 查询必须在快照配额判定之前

主 AI **CHANGE**:KV 查询落在 `loadLiveAccount` 之后、`denyQuota` / `assertAllowed` 之前。
依据:`design.md:357`「①③④ → 查 KV → 未命中才 UPDATE」;`requirements.md:95`;
AC-SESS-10 E2E 明文要求 `max_sessions=1` 响应丢失后同 key 重试成功且 `used_sessions` 恒为 1。

已落地:`share-auth-service.js:346-358` + 用例
`replays a max_sessions=1 share after the first slot is gone (AC-SESS-10)`。
换 key 仍走 `quota_snapshot` 拒发。吊销/过期后 ≤120s 窗口内重放仍可能吐出缓存 token,
回源 `resolveSession` 打死——与 AC-EDGE-13 TOCTOU 同类,不构成越权。

### R-T07-2 · [P2] 重放不校验缓存与当前行的一致性

缓存值里的 `expiresAt` 是首发时刻的快照。首发之后 Owner 若延长/缩短有效期,重放
(≤120s 窗口内)返回的仍是旧 `expiresAt`。token 本身携带的 `exp` 也是旧的,回源时以行为准,
所以不构成越权,只是响应里的展示字段可能陈旧 120 秒。design.md 要求「响应形状与首发一致」,
这里按字面实现;若后续要求「值也随行走」,得改成只缓存 token、其余字段重算。

### R-T07-3 · [P2] `Idempotency-Key` 未做长度/字符集约束

`share-api.js` 只做 `|| ''`,service 只做 `trim()`。一个超长 key 会拼进 KV key
(Workers KV 键上限 512 字节),超限时 `put` 抛错 → 被 fail-open 吞成 `share.system.error`,
行为安全(仍签发)但会刷日志。要不要在 API 层截断/拒绝,建议与 T-08 一并定。

### R-T07-4 · [P3] 幂等键不绑 `sec`

key 由客户端生成、只绑 `lid`。同一 `lid` 的两个持链者若撞了同一个 key,后者会拿到前者的
token。但走到重放查询前双方都已通过 `sec`(及后续 AuthKey)校验,即两人本就是同权持链者,
拿到同一 token 不越权。design.md:243 已把这条论证写死,此处只做记录。

### R-T07-5 · [P3 · 非漏登记] 前端侧未接线

design.md:240 要求访客页在发请求**前**生成 key 并写 sessionStorage(`share:est-key:<lid>`)。
T-07 只落服务端是规格分工;前端接线由 **T-26** 承载,不是漏登记。

===== 固定模板:真实完成与端到端验证报告评审(artifact-verification)=====
审的是实现完成后的验证报告。目标不是统计改了多少文件或多少测试通过，而是证明：**原始用户目标在真实运行链路中已经达成，所有关键产出被正确消费者使用，且没有引入不可接受副作用**。

逐条检查：
1. 原始目标、失败前状态和可观察成功判据是否逐项对应，不能把‘实现已合并’当完成。
2. 是否从真实入口跑到最终用户/外部系统结果，并提供每一跳的输入、输出、状态变化和证据锚点。
3. 接口 200、单测绿、日志出现、数据库有记录、消息已发送都只是中间证据；必须证明正确下游消费者收到并产生目标业务效果。
4. 是否覆盖原失败样本、正常对照、边界、并发/重试/乱序、失败恢复、多租户/权限和历史数据。
