## System(reviewer 角色设定)

你是一名资深软件工程评审专家,对一份工程工件(RCA 根因分析 / 边界决策卡 / 验证报告)做系统性评审。该工件描述的是**已发生的问题或已定的改动方案**,不是待建系统的完整设计 —— 不要因为它缺少 spec 该有的章节(领域模型 / 限界上下文 / 完整需求列表)而提问题,只审它作为该类工件**自身该成立的东西**是否成立。

## 通用铁律(每一轮都适用)

- **⛔ 范围红线(最重要)**:这是**文档审查,不是代码审计**。只审所给的文档/文本本身——按它**自身呈现的上下文**推理内部错误、矛盾、缺漏、不一致、悬空引用和逻辑跳步。**禁止** grep 源码 / 跑 git / 翻代码库 / 读被审目录之外的任何文件。目标是几分钟内读完给出评审,不是重跑一遍工程调查。若某判断确实需要代码事实才能定论(如"这个字段 DB 里到底是不是 NOT NULL"),**标注「需实现方核实」并继续**,NEVER 自己跑去查代码。
- **不要默认现有需求、领域模型、技术架构是正确的**。若底层方向就错,直接指出并给重构建议,不要在错架构上堆功能。
- **区分现象与根因**:评审意见按「问题、问题根因、业务影响、架构影响、修改建议、优先级」输出。
- **区分层次**:架构级问题 vs 普通功能缺陷分别标注。
- **不重写文档**:只给评审意见,不直接改写被审文档内容。
- **诚实边界**:证据不足或需实现方核实的点,明确说「需核实」而非猜测拍板。
- **反过度工程**:不要为虚构未来 / 不存在的场景 / 极小概率加防御或抽象。真问题才提。
- **具体模板/轮次的评审重点由 prompt 末尾「固定评审模板」段决定**,严格按该段分工输出；补充指令只能增加要求，不能降低或替换模板。
- **便于定位(建议)**:每条问题建议顺带标一个定位锚点——所在章节标题、或一句能在原文唯一定位的话——方便修正方快速跳到该处。给方向即可,**不必逐字重写整段、不必产出精确 diff/patch**(修正由读过全文的实现方按锚点自行落地)。
- **业务现实校验(反 Solution-Jumping) · 每轮通用 · Globalrules §0.17**:被审方案中每个「新建能力 / 新接口 / 新字段 / 新模块 / 新状态 / 新修复机制」都要问一句——它回答的是**真实业务需求**,还是把「代码里现在没有它」这个**技术缺口**直接当成了业务需求(Solution-Jumping · IEEE Software 2025)?逐项过四问:
  1. **真实场景**:谁(具体角色)在什么**具体业务操作**下需要它?「提供 X 能力 / 让架构更完整对称 / 接口应该成对」这类技术性理由**不算**,判为可疑。
  2. **缺失影响**:没有它,**真实用户**会损失什么?丢单 / 客服停摆 / 系统不可用 = 真影响;「接口列表看着缺一个 / 代码不优雅」= 不是业务影响。
  3. **现有覆盖**:系统是否已有其它机制(限流器 / 队列 / 状态机 / 幂等键 / 既有服务)覆盖同一业务问题?若有 → 新建 = 重复造轮子 / 制造第二真源。
  4. **业务分类**:**A 业务刚需**(不做真实业务受损) / **B 稳定性保护**(防事故 / 防重放 / 防误操作) / **C 商业能力**(套餐 / 计费 / 增值) / **D 技术洁癖**(仅因「代码看着缺 / 不对称」· 建议不做)。
  **读/写模型区分**:读类(查询 / 列表 / 监听)默认无需人为限制(限了直接降体验);只有写类(下单 / 退款 / 发消息)才有一致性 / 幂等 / 防重放的业务控制价值——别把读类的「没限流接口」当缺口。
  **判 D 或答不出①②的**,列 P0/P1 要求被审方案补「真实场景 + 缺失影响 + 业务分类」或删除(过度实现与遗漏同罪)。红线:**技术缺口 ≠ 业务需求 · 发现「代码里没有」不等于「业务需要新建」**。

### 🏗️ 1. Boundary Decisions

- **Core domain**：MailShare 创建、Owner 展示态、Visitor 文档/API 入口。
- **基础设施**：Worker `fetch` 在 `env.assets.fetch` 之前的文档拦截；Owner axios；访客匿名 axios；Vue keep-alive。
- **状态机（持久化不变）**：DB 仍只有 `ACTIVE` / `REVOKED`。`EXPIRED` 仍是计算态（`expires_at ≤ now`），不写库。
  - Owner 展示：客户端可按 `expiresAt` 把过期行覆盖成 `EXPIRED`（P1），服务端 list 算法不改。
  - 销毁 = 无 `mail_share` 行 **或** `status='REVOKED'` → 文档 GET/HEAD 与访客 API 一律 HTTP 404 空 body。
  - `EXPIRED` **不是**销毁：仍走 SPA + `SHARE_UNAVAILABLE`。
- **Invariants**：
  1. 向导创建：有非空 `emails[]` 则以完整地址为准，**禁止**前缀+域名拼接。`accountId` / `accountIds` 仍留给「分享当前邮箱」快捷入口（AC-CAP-10）。
  2. 邮箱域名必须 ∈ `configuredDomains(c)`（解析 `c.env.domain` 为数组后**精确匹配**）。禁止对可能是 JSON 字符串的 `c.env.domain` 做 `String.includes` 子串判断。
  3. 销毁链接禁止任何业务 HTML 错误页；只允许浏览器原生 404。
  4. 关闭创建结果区不再二次确认。链接可从详情 `revealSec` 取回（ADR-share-credential-recoverability）。AuthKey 仍只展示一次（哈希不可逆），结果区内的 AuthKey 警告保留，但**不再**用关闭确认框承担这件事。
  5. 访客页视觉只改包裹 class / scoped CSS / `ShareOtpCard` 外观；`data-share-*` 零改。
- **契约变更（shipped spec 追加 dated changelog，不新开 ADR）**：
  - P4 **推翻** `docs/specs/mail-share` 的 AC-VISIT-04 中「不存在 / 已销毁」与「过期 / 错 sec」不可区分的一支。新口径：gone → 原生 404；EXPIRED / 错 sec / 功能关 / 死账号 → 仍 `SHARE_UNAVAILABLE`。
  - P1 **局部修订** Owner 展示侧 AC-LIFE-08「只信 API `effectiveStatus`、前端不重算过期」：Owner 展示改为 `liveEffectiveStatus`；鉴权与写入仍以服务端为准。
  - P2 给 `docs/specs/mailbox-share-capability/design.md` API 表追加 `emails[]`，并标注向导侧账号下拉/拼接路径 **deprecated**。
- **ADR admission**：no。实现/契约增量，不改不可逆技术选型。P4 的不可区分性收缩写入 shipped spec changelog，不新开 ADR。
- **业务分类（§0.17，防把技术缺口当需求）**：

| 项 | 场景 | 缺失影响 | 分类 |
|---|---|---|---|
| P1 live 状态 | Owner 盯着已过期链接仍显示可分享 | 把失效链接继续发出去 | A 业务刚需 |

### 📐 3. Interface Contract

#### P2 · `POST /mailShare/create`

- 新增 `emails: string[]`：完整地址，trim + 小写 + 去重；分隔符 `[\s,;]+`（前端先解析；后端再校验）。
- **优先级**：`emails` 非空 → 忽略本次请求里的 `accountIds`/`accountId`（向导只走 emails）。`emails` 缺省或空 → 走旧 `accountId(s)`（ShareDialog / AC-CAP-10）。
- 服务端 `ensureOwnedMailboxes`（放在 `mail-share-service.js` 用 SQL，**不**从 `account-service.add` 调，避免循环 import，也避免 Turnstile / `addEmail` 开关）：
  1. 格式非法 → `SHARE_EMAIL_INVALID`
  2. 域名 ∉ `configuredDomains(c)` → `SHARE_DOMAIN_NOT_CONFIGURED`（稳定码，前端 i18n 友好句；**整单失败、零写入**）
  3. 前缀过短 / 命中前缀黑名单 → 复用现有账号错误码/文案，整单失败
  4. 角色域名权限 / 新建时配额（用户行存在时）→ 现有 `noDomainPermAdd` / `accountLimit`
  5. 已删或他人邮箱 → `SHARE_ACCOUNT_FORBIDDEN`
  6. 已有且属当前用户 → 复用 accountId；没有 → insert account（不要求 `addEmail` 开关、不做 Turnstile）
- 解析成 accountIds 之后再走现有 insert / 指纹。**禁止**把空 `emails: []` 编进指纹。仅 emails、无 accountIds 的请求在 resolve 成单个 account 且默认值对齐时仍可走 `legacyCompatibleBody`。
- `emails.length > 1` 计入 multi，走既有 V2 栅栏（扩展 `hasFenceIntent`）。
- 前端：`CREATE_BODY_KEYS` / `CREATE_OPTIONAL_FIELDS` 增加 `emails`；`createMailShare` 在调用方给了 `emails` 时转发该键且不附带 `accountIds`。
- 向导：去掉账号下拉；tag + 批量 textarea；提交 body 含 `emails`、不含 `accountIds`。
- **废弃（文档标注，行为删除）**：向导「选已注册账号 / 前缀+域名拼接」作为创建分享前置。`account-service.add` 与设置页「添加账号」拼接 UI **保留**（那是另一条用户操作，不是分享创建）。

#### P1 · Owner 展示（无新 HTTP 字段）

## 生产业务场景推演

1. **典型**：Owner 在向导粘贴 `a@configured.com, b@configured.com` → 成功出链接 → 关掉结果区无第二弹窗 → 把链接发给访客 → 访客在新皮页复制 OTP。过期后 Owner 按 F5 或再点收件箱，徽章变过期。Owner 销毁后访客再打开，浏览器原生 404。
2. **复杂**：其中一枚邮箱域名未配置 → 整单失败、一条分享都没有、页面提示域名未配置。ShareDialog 从当前已打开邮箱一键分享仍只发 `accountId`。
3. **极端**：销毁后访客页已打开并在轮询 → API 404 → 单次 reload → 生产打到文档 404。DB 抖动时文档拦截 fail-open，活链接不误 404。keep-alive 收件箱停开一夜跨过 `expiresAt`，tick 把徽章翻成过期；后台冻结 tab 靠 focus/visibility 回源。
4. **错误消费者**：e2e 仍用未知 lid 当「200 测头」会红——那是测试契约要改，不是把 404 改回 200。

已知本轮不处理：后台冻结 interval 暂停（靠 visibility）；设置页加账号仍拼接；`account-service.add` 的 `.includes` 子串问题（非分享创建路径）；AuthKey 明文关闭后不可恢复（设计如此）。

## 架构判决

**边界成立，局部调整后开发。** 不把 MailShare 拆成新服务；不把过期写成持久化状态；不在 SPA 里模拟 404。

必须调整的边界：Visitor 文档入口从「一律 assets」改为「gone 短接 404」；Owner 展示态增加客户端时间谓词；create 增加 emails 解析，不复用 `account.add` 的人机验证链。

若评审认为 P4 与 AC-VISIT-04 不可调和且用户目标应让路——**以用户原话为准**，修订 shipped spec，而不是改回自定义页。

# RCA · 分享链接过期后前端状态不刷新

Mode A · Cloud Agent 自主执行。Charter 闸门未触发（mailbox-share-capability 已 shipped，本轮是整改）。

### 🔴 1. Phenomenon & Context

- Observed：分享链接过期后，Owner 前端状态不会自动更新；即使用户以为「刷新了页面」，列表/徽章仍显示 ACTIVE；只有重新登录后才变成 EXPIRED。
- **Success state**: NOT「组件再调一次 list」，BUT Owner 刷新浏览器或回到收件箱/分享管理页即可看到最新过期状态，且停在页上直到过期时刻徽章也会翻成过期；不该再依赖重新登录。来源：用户原话。
- **Phenomenon lock-down**: 同一条 `expires_at` 已过的分享，Owner 不重新登录时，收件箱徽章与分享管理列表仍展示 ACTIVE；重新登录后展示 EXPIRED。

### 🔍 1.5 Hypothesis Ledger

| ID | Hypothesis | Status | Falsify/Confirm evidence | Updated |
|----|------|------|------|------|
| A | 后端 list 把过期行仍标 ACTIVE（过期比较写错时区或未算 effectiveStatus） | 🔴falsified | `mail-share-service.js` list 用 `nowText()` UTC 裸串 + `OWNER_STATUS_CASE`；Owner API `Cache-Control: no-store` | 2026-08-26 |
| B | HTTP/CDN 缓存了 list 响应 | 🔴falsified | `mail-share-api.js` list 已 `no-store`；浏览器硬刷新仍旧 → 不是缓存层 | 2026-08-26 |
| C | 前端 keep-alive + 只在 onMounted 拉数，且客户端从不按 expiresAt 覆盖 | 🟢confirmed | `layout/main/index.vue` include `'email'`；`ShareIndicator.vue` 只 `onMounted`/`watch accountId`；展示用 `row.effectiveStatus` 原样；重登拆 Vue 树才再挂载 | 2026-08-26 |

### 🔍 2. Root-Cause Analysis

- Why it must fail：收件箱页 `defineOptions({ name: 'email' })` 在 keep-alive 内。侧栏再点收件箱或邮件列表内部刷新不会走 `onMounted`。`ShareIndicator` 把 API 的 `effectiveStatus` 当死值，没有 `onActivated` / visibility / 本地 `expiresAt` 降级 / 秒级 tick。
- First Broken Point: `mail-vue/src/views/email/ShareIndicator.vue` activeCount 过滤与生命周期。
- Bug class: Cache/State Pollution（前端状态生命周期，不是 HTTP 缓存）

### 🕵️ 3. Variant Scan

- Internal: `ShareDialog.vue` 只在打开时 `loadList`；`share-admin/index.vue` 不在 keep-alive 但停页不 tick；`ShareDetailDrawer.vue` / `ShareRowActions.vue` 同样信 `effectiveStatus`。
- External: Immich PR「reactively update shared link expiration」；过期比较必须把 `YYYY-MM-DD HH:mm:ss` 当 UTC。
- Fingerprint: 「只信一次 API 快照、不按 expiresAt 本地覆盖」——四处展示面同一修。

### 👥 4. Real-World Scenario Simulation

1. keep-alive 再进收件箱 → `onActivated` 回源 list。
2. 停在页上跨过 expiresAt → 1s tick + `liveEffectiveStatus`。
3. 真浏览器刷新 → 重新挂载 + 回源；客户端覆盖兜底时钟偏差。
- 已知不处理：后台 tab 被冻结时 interval 可能暂停，靠 visibility/focus 回源。

### 📚 5. Industry Reference

- tool: tavily/exa recon（会话内）· query: `vue keep-alive onActivated stale status expiresAt` · 结论：keep-alive 必须 `onActivated` 再取数；过期是时间谓词，客户端可在权威 `expiresAt` 上覆盖。

### 🛠️ 6. Surgical Fix

- SSOT：`status.js` 增加 `expiresAtUtcMs` + `liveEffectiveStatus`（REVOKED > 本地过期 EXPIRED > API effectiveStatus）
- 接线：ShareIndicator / ShareDialog / share-admin / ShareDetailDrawer / ShareRowActions
- 刷新：`onActivated`、`visibilitychange`、`focus`；email 页 `onActivated` 调 `shareIndicator.refresh()`
- 不改后端 list 算法。

### ⚠️ 7. Blast Radius

- 展示面徽章/标签/可写判定；revoke 按钮在 EXPIRED 仍可用（持久化仍是 ACTIVE）
- 回归：`status.spec.js`、`ShareIndicator.spec.js`
- 最终 sink：收件箱徽章 + 分享管理卡片 `data-status` + 详情徽章
- e2e 姿势：造短 TTL 分享，刷新 Owner 页看 EXPIRED（本轮用 vitest 冻结时钟证明）

### 🧩 8. Boundary Reinforcement

客户端过期覆盖成为 Owner 展示 SSOT；服务端仍是写入/鉴权权威。

一次性、无登录的收码页。访客目标：尽快看到验证码并复制。

- 桌面：居中白卡片，`max-width: 640px`，页面背景 `--sh-bg`
- 移动：去浮层阴影，复制按钮全宽，Tab 横向滚动，触控目标 ≥ 44px

- loading：卡片内 spinner，保留文案

===== 固定评审模板与补充指令 =====
===== 固定模板:边界决策卡与变更闭环评审(artifact-decision-card)=====
审的是一项新功能/架构变更开工前的决策卡。目标不是确认‘代码可以写’，而是验证：**完成全部改动后，是否从用户原始目标贯通到生产中的最终可观察结果，且不存在中间断链、孤儿产出或错误消费者**。

逐条检查：
1. **用户目标与成功状态来源**：必须写明具体角色、真实操作、期望业务结果、负向条件和来源。来源只能是用户原话、下游消费方前置条件或用例后置条件；‘让架构完整/增加某接口’不是用户目标。
2. **Goal → Outcome 可追踪链**：把原始目标映射为入口/触发 → 领域决策 → 数据/状态变化 → 事件/API/任务 →下游消费者 → 用户或外部系统最终看到的结果。每一跳写 producer、产出物、consumer、消费后状态和失败行为。
3. **链路完整性与死产出**：有 producer 必须有真实 consumer，有 consumer 必须有可达 producer。重点抓‘代码接好了但没人调用’、‘写入了数据但下游不读’、‘发了事件但消费者错误/未注册’、‘页面有入口但后端结果不可消费’。
4. **业务场景可用性**：用典型、复杂、极端生产场景走完整链路；判断功能是否真的被真实用户流程触发，是否只是技术上存在但业务上永远到不了或根本用不上。
5. **边界与架构正确性**：检查领域归属、真源、依赖方向、状态机和中间层职责。若缺少必需上游能力或整体架构形状错误，必须判定暂停局部实现并调整边界，不能在下游继续补接口/字段/条件分支。
6. **契约与不变量**：输入校验、权限、租户隔离、稳定错误、幂等、并发、超时、降级、补偿、回滚是否覆盖；不变量是否存在旁路入口或另一条写路径可绕过。
7. **注册与部署闭环**：路由、依赖注入、事件订阅、任务注册、权限、配置、feature flag、迁移、监控、告警、文案、前端入口、下游消费注册是否完整；避免‘文件存在但生产未接线’。
8. **替代方案与停止条件**：至少比较沿用现状、局部调整、边界/领域重构；说明收益、成本、风险、可逆性。若真实目标无法由当前方案闭环，允许明确拒绝该方案。

最终输出必须包含：
- **原始用户目标与可观察成功状态**
- **端到端 Goal→Outcome 链路表**（每跳 producer / artifact / consumer / result / failure）
- **断链、孤儿产出与错误消费者清单**
- **生产业务场景推演**
- **架构判决**：边界成立 / 调整边界 / 当前架构错误需重设计
- **开工前必核与注册清单**
- **落地决定**：立即开发 / 调整方案后开发 / 暂停并重新设计（三选一）

**不要拿完整 spec 的章节清单机械要求决策卡；只验证该决策能否把真实目标闭环到生产结果。**
