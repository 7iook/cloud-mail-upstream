# 第 2 轮评审结论

## 总体判断

R1 提出的授权会话、状态机、范围查询等缺口已有明显收敛，资源级 capability、动态过期和 scoped repository 可以保留。

但反向验证后，当前方案仍把三个相邻问题塞进 MailShare 首版：验证码识别升级、全站渲染器迁移、分布式长轮询控制。它们扩大了交付边界，其中验证码双路识别还会形成第二套领域真源。

另有一个阻塞性领域错误：`regenerate` 同时被定义成“凭据轮换”和“让过期授权重新 ACTIVE”，但没有重新建立授权期限，当前状态机无法实现。

## 一、架构级问题

### R2-A1 · OTP 打分被放进分享投影链，形成第二套验证码真源

**定位锚点：** requirements.md「#### 双路合并策略（F1 · 用户 R1 裁决）」

- **问题：** `otp-scorer` 由 `share-mail-service` 调用，Visitor 获得确定性候选、置信度和双候选，而既有 `email.code` 及其他消费者仍使用原结果。同一封邮件因此可能在分享页和其他渠道显示不同验证码。
- **问题根因：** 把“分享页需要方便复制验证码”直接跳成“分享模块新建验证码识别系统”，没有先证明现有 `email.code` 在真实业务样本上不能满足需求。
- **业务影响：** 用户可能在不同渠道看到相互冲突的验证码；管理员调整阈值还会只改变分享页行为。
- **架构影响：** OTP 识别属于邮件摄取/内容理解领域，而非授权投影领域。当前方案新增候选模型、阈值、HTML 转文本和 DTO 字段，制造第二真源。
- **业务现实分类：** 当前证据下属于 **D 技术缺口驱动**；若有真实误报/漏报数据，可升级为 **A 业务刚需**，但仍应归属邮件处理域。
- **修改建议：** 首版分享只消费邮件域已有的权威 OTP 结果。若真实样本证明需增强，应把统一抽取、归一化、候选合并移到邮件处理链，使所有消费者读取同一结果；不要在 Share 投影时重新推断。
- **优先级：P0**

### R2-A2 · `regenerate` 混淆“凭据轮换”与“创建新授权”，过期记录无法真正恢复 ACTIVE

**定位锚点：** design.md「#### 状态迁移表」

- **问题：** 状态表允许对 `EXPIRED` 记录重新生成，并宣称 `effectiveStatus → ACTIVE`，但操作只更新 `lid` 与 `sec_hmac`；接口没有新时长，迁移也没有更新 `expires_at`。原过期时间仍在过去，新链接会立即被计算为 `EXPIRED`。
- **问题根因：** 把授权政策（可见窗口、有效期）和授权凭据（lid/sec）合并进一个“重新生成”动作。
- **业务影响：** Owner 对过期分享点击重新生成后可能拿到一条仍不可用的新链接。
- **架构影响：** 凭据轮换本应保持授权边界不变；过期后再次授权则是新的业务授权，应重新确认期限及 Visible Window。二者共用同一状态迁移会破坏审计语义。
- **修改建议：** 二选一并统一需求、接口和状态机：  
  1. `regenerate` 仅允许 ACTIVE，用于轮换凭据并保持原到期时间；过期后必须新建授权。  
  2. 若允许过期后重新授权，则把它建模为显式的新授权操作，重新给定期限和窗口，而非同行“复活”。
- **优先级：P0**

### R2-A3 · 服务端长轮询把“秒级刷新”升级成缺少协调底座的分布式连接管理

**定位锚点：** requirements.md「#### 读模型契约（A5）」

- **问题：** 文档一方面确认 Workers 请求间无共享内存，另一方面要求精确限制“单条 Share 最多 5 个 in-flight wait”，却没有连接租约、原子占用、异常释放或过期回收模型。现有辅助表也没有对应状态。
- **问题根因：** 为追求约 1 秒延迟，先选定服务端长轮询，再反向增加连接控制规则掩盖运行模型不匹配。
- **业务影响：** 上限可能无法执行，或异常断连留下幽灵占用；合法访问者可能持续被拒绝。
- **架构影响：** 每个 Visitor 最多触发 25 次 D1 查询，还需额外引入分布式租约写入，复杂度已接近文档明确拒绝的协调基础设施。
- **业务现实分类：** 自动出现新邮件是 **A**；“1 秒服务端长轮询”和“精确 5 连接”只是实现方案，并非业务需求。
- **修改建议：** 优先比较更简单的客户端定时增量查询是否已满足“秒级出现”。只有经过容量测算确认普通轮询不达标，才保留长轮询，并补齐可实现的共享租约模型；否则删除 in-flight 分布式计数能力。
- **优先级：P1**

### R2-A4 · 幂等方案只能确认操作发生，不能恢复丢失的 Secret，且存在两个幂等真源

**定位锚点：** requirements.md「**幂等与并发语义（A4）**」

- **问题：**
  - 重放只返回 `shareId/lid` 而不返回 `sec`，所以它并不能重放原成功结果；用户仍需销毁或再次 regenerate。
  - design.md 同时在 `mail_share.idempotency_key` 和独立 `share_idempotency` 表记录幂等信息，生命周期与权威来源不明确。
- **问题根因：** “Secret 只返回一次”和“响应丢失可恢复”两个目标没有在协议层统一，只在末端增加幂等记录。
- **业务影响：** 网络抖动会产生无法使用但仍有效的授权；regenerate 响应丢失还会先废掉旧链接。
- **架构影响：** 两个幂等存储会产生清理、唯一约束和历史重放不一致。
- **修改建议：** 明确这是“重复操作检测”还是“可恢复幂等”。若必须恢复，应调整 Secret 生成/提交协议；若接受不可恢复，应明确用户代价并简化为单一幂等真源，删除重复字段。
- **优先级：P1**

### R2-A5 · 访问指标不能证明“收件人已交付”，却把关键读路径永久变成写路径

**定位锚点：** requirements.md「**本期保留的管理字段及其业务场景**（用户 R1 裁决 · F3）：」

- **问题：** `access_count` 和 `last_access_at` 只证明某个持链者成功建立过 Session，不能证明目标收件人已阅读或拿到验证码；重复刷新、自动化访问和链接转发都会污染语义。
- **问题根因：** 用技术上可采集的鉴权事件替代业务上不可直接观测的“交付/阅读确认”。
- **业务影响：** Owner 可能根据不可靠指标误判对方已经收到验证码；指标还会引入额外隐私预期。
- **架构影响：** 原本只读的 Session 建立变成数据库写操作，增加延迟、写放大和并发失败面。
- **业务现实分类：** 当前不满足 **A**；更接近待验证的管理分析能力。若只用于异常访问提示，可归 **B**，但需要重新定义语义。
- **修改建议：** 不要把它表述成“已交付/已使用”的证明。首版优先删除计数，或仅保留语义明确的最近成功鉴权时间，并明确它不代表阅读确认。
- **优先级：P1**

### R2-A6 · D1 限速与全局指标系统的成本可能高于其防护价值

**定位锚点：** requirements.md「### Requirement 9: 滥用防护（本期最小）」

- **问题：** 方案已经承认 256-bit Secret 不可枚举，却仍为每次失败建立 D1 来源计数和全局滑动窗口指标。攻击者可制造大量来源键，把保护逻辑本身变成持续写入面。
- **问题根因：** 从“系统需要防滥用”直接跳到“业务库内自建限速和指标系统”，没有先判断边缘平台或既有监控是否覆盖同一问题。
- **业务影响：** 正常 NAT 用户可能互相影响；超限统一映射为 `SHARE_UNAVAILABLE`，客户端也无法判断何时可重试。
- **架构影响：** `CF-Connecting-IP + first-XFF` 的信任关系未闭合；需实现方核实 XFF 是否可能含客户端可控部分，以及现有边缘限速/监控能力。
- **业务现实分类：** 防事故属于 **B**，但当前两张新表及自建告警链尚未证明必要。
- **修改建议：** 先核实现有平台级限速与监控；优先在可信边缘做粗粒度保护。只有存在明确滥用模型和告警消费方时，才落业务库计数；同时不要把可恢复限速伪装成永久不可用。
- **优先级：P1**

### R2-A7 · 全站渲染器修复方向正确，但不应被隐藏成 MailShare 内部组件改动

**定位锚点：** requirements.md「### Requirement 6: 正文安全渲染（双模式）」

- **问题：** Share HTML 模式依赖安全渲染是真需求，但方案同时替换登录态详情页的既有渲染器，形成跨领域、全站爆炸半径，却仍作为 MailShare 首版的一部分交付。
- **问题根因：** 为避免重复实现，正确选择了统一渲染器，却没有同步调整交付边界。
- **业务影响：** 登录态正文兼容性回归会阻塞分享功能上线；反过来，为赶分享功能又可能压缩全站安全迁移的验证。
- **架构影响：** 这是平台安全组件，不属于 MailShare bounded context；但又必须作为 Share HTML 模式的前置依赖。
- **业务现实分类：** **B 稳定性/安全保护**，应保留，不是技术洁癖。
- **修改建议：** 保留单一 `SafeMailRenderer`，但将其明确为独立的平台安全前置工作及独立验收边界；MailShare 只依赖其稳定契约。在该前置未完成前，分享页只能提供纯文本模式，禁止临时造第二个净化器。
- **优先级：P1**

## 二、普通功能缺陷

### R2-F1 · Fragment 清除后，会话在刷新、后退和页面崩溃场景下没有恢复契约

**定位锚点：** design.md「| **Fragment 清除** |」

- **问题：** 页面立即清除 `sec`，但没有定义 `sessionToken` 只驻留内存、放入 `sessionStorage`，还是其他位置。若仅驻留内存，刷新后 URL 已无 `sec`，页面无法重新建立 Session。
- **问题根因：** Secret 清除与页面恢复分别设计，隐含假设页面生命周期内不会刷新、崩溃或被浏览器回收。
- **业务影响：** Visitor 在等待验证码时刷新页面会突然失去访问能力，只能重新寻找原始链接。
- **架构影响：** bearer token 的存储位置还决定 XSS 暴露面、多 tab 共享和关闭页面后的生命周期，不能由实现方自行猜测。
- **修改建议：** 明确刷新、后退、页面恢复和多 tab 的产品语义，并据此规定 Session 凭据存储及清理边界；如选择不可恢复，也应在交互和验收条件中明确。
- **优先级：P1**

### R2-F2 · `Reveal` 是悬空领域概念

**定位锚点：** requirements.md「- **Reveal**：Visitor 显式发起的、消耗性的取内容动作」

- **问题：** 文档定义了消耗性 Reveal，但本期没有访问次数、阅后即焚、Reveal 接口或对应状态迁移。
- **问题根因：** 旧方案或未来能力的术语残留。
- **业务影响：** 实现方可能误以为建立 Session 或读取详情需要额外的消耗性语义。
- **架构影响：** 给纯读路径引入不必要的状态变化倾向。
- **修改建议：** 本期删除该术语；未来真正引入阅后即焚或次数限制时再定义。
- **优先级：P2**

## 三、三种路径对比

| 路径 | 收益 | 成本 | 主要风险 | 技术债判断 |
|---|---|---|---|---|
| **沿用现有方案** | 可直接按当前任务矩阵开工 | 首版同时建设授权、OTP、渲染平台、限速指标、长轮询协调 | 第二 OTP 真源、过期 regenerate 不可实现、跨模块回归面过大 | 高，不建议 |
| **局部重构（推荐）** | 保留 capability、状态计算和 scoped repository；OTP 回归邮件域；简化实时刷新；SafeMailRenderer 独立为前置 | 需调整任务拆分和部分接口 | 上线范围需要重新排序 | 可控，最符合严格最小集 |
| **领域重构** | 抽象通用 ResourceGrant/Capability 服务，未来可复用到附件等资源 | 需重做授权对象、策略、事件和迁移 | 当前只有一个明确业务场景，容易过度设计 | 暂不值得 |

## 四、保留、调整与停止开发清单

### 可以保留

- `lid + sec` capability URL 及 fragment 承载。
- 持久化 `ACTIVE/REVOKED`、实时计算 `EXPIRED`。
- `ShareScopedEmailRepository` 与固定 Visitor DTO。
- 逐请求回源校验、撤销即时生效。
- 附件不进入首版。
- 单一 SafeMailRenderer 的长期方向。

### 必须调整

- OTP 识别的领域归属及单一真源。
- `regenerate` 的业务语义和状态迁移。
- 长轮询及并发上限的实现路线。
- 幂等恢复协议与幂等 SSOT。
- 访问指标的真实语义。
- Session 在 fragment 清除后的恢复策略。
- SafeMailRenderer 与 MailShare 的交付边界。

### 应停止继续开发

- 在 Share 投影链内新增独立 OTP 推断系统。
- 允许过期授权通过只换 `lid/sec` 原地复活。
- 在没有共享租约模型时实现“精确 5 个 in-flight wait”。
- 在未核实现有平台能力前建设 D1 全局指标与来源限速子系统。
- 把 `access_count` 当作收件人已阅读或已交付的证据。
